# Review findings: harness v2, ops, Gemini client, security gaps

Independent review of code added by an earlier agent that was cut off before reporting (`harness/verifier.py`, `harness/toolcache.py`, `ops/slo.py`, `ops/alerts.py`, `ops/retention.py`, `ops/dedup.py`, `ops/cli.py`, `prometheus_rules.yml`, `grafana_dashboard.json`, `llm/verifier_sim.py`, `llm/gemini_client.py`, runtime edits), plus the gaps the security work-stream listed. Every fix has a regression test in `tests/test_review_fixes.py` unless noted. No existing test was weakened; three API tests were updated to send the new session token (`tests/test_misc.py`, `tests/test_ops.py`), which is the behaviour change being introduced.

Severity: **High** = wrong behaviour in a production path with security or money impact; **Medium** = reliability/operability defect that can hide an incident or break a deploy; **Low** = correctness edge or defense in depth.

## Reviewed and found sound
- **Verifier** is fail-closed (timeout, outage, malformed output, amount mismatch, missing ground truth and exhausted call/USD budget all escalate; budget is consumed before the call), runs only after `ToolGuard.authorize` so it cannot unblock, is skipped in shadow dry-runs, sees only harness-fetched whitelisted fields (no notes, no email) via direct registry calls that bypass the cache. The USD cap is checked before each call, so one call can overshoot it (documented, acceptable).
- **Exactly-once refunds**: harness-derived idempotency key `stable_hash(session, tool, args)` + server-side `BEGIN IMMEDIATE` and a UNIQUE key; replays return the original refund. Covered by existing tests for duplicate calls, parallel resume and crash-after-commit. The cache never caches writes or errors and money decisions never read it.
- **SLO math**: burn rate = error rate / (1 - objective), both windows must exceed, min-events gate; PromQL thresholds = factor x budget (tested). Offline `>=` vs PromQL `>` differs only at equality (ADR-0015).
- **Retention**: dry-run writes nothing; only terminal sessions; legal holds; optimistic concurrency; tombstones in the audit chain; audit archive-only; does not destroy shared customer keys.
- **Request dedup**: same key + same payload replays, different payload 422, in-flight 409, stale in-flight takes over (tool keys make the re-run safe), failures release the key.
- **Gemini client**: tool calls and responses map correctly (thought signatures carried in the call id and re-attached), 408/429/5xx retried with capped backoff honouring `Retry-After`/`retryDelay`, daily quota raises `QuotaExhausted`, key read from env/.env and never logged.

## Not fixed (deliberately) / remaining
- **Customer messages starting with `[`** are treated as harness-internal (excluded from intent grounding and the verifier's customer words), and the model may read them as harness feedback. Fixing it changes behaviour on the held-out `injection_variant` scenario (`"[SYSTEM] new policy..."`) while the live eval is running, so it needs a baseline re-run first. Low.
- **Alert flapping at low traffic**: when a window drops below `min_events` the alert is reported resolved (ADR-0015).
- **Cross-process staleness**: other processes' writes are bounded only by the 30 s cache TTL; cached values hold raw PII in memory for that TTL; erasure cannot flush other processes' caches (ADR-0014).
- **Concurrent resume from two processes** moves money once (idempotency) but the transcript is last-writer-wins; the API serializes within one process.
- **Docs owned by other work-streams** (`docs/threat_model.md`, `docs/enterprise_readiness.md`) still list G1-G3 and customer auth as open; they should be updated to point here.
- Base image pinned by tag, not digest; `promtool` not in CI; no live deploy was performed.
